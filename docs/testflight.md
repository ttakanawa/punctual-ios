# Deploy a branch to TestFlight

## Protect deployment tags in GitHub

1. For first-time setup, inspect all existing tags beginning with `punctual-testflight-v1-` before configuring Apple distribution. Confirm that any tags you intend to keep point directly to the full SHA in their names and contain the current archive checks.
2. Keep one **Active** tag ruleset for `punctual-testflight-v1-*` and `punctual-testflight-v1-*/**/*`, with no exclusions. The second pattern covers slash-containing names that match Apple's prefix. Enable **Restrict updates** and **Restrict deletions**. Leave **Restrict creations** off and leave the bypass list empty, including for administrators and Apps. In the API, both include patterns start with `refs/tags/`. Save the ruleset ID in the **repository variable** `TESTFLIGHT_TAG_IMMUTABILITY_RULESET_ID` so the tag job can read it outside the Apple environment. [GitHub tag patterns](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/creating-rulesets-for-a-repository#using-fnmatch-syntax) and [ruleset controls](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets#restrict-updates).
3. To migrate the previous two-ruleset setup, first verify that the existing immutability ruleset is active with both patterns and an empty bypass list. Keep it active throughout migration and copy its existing ID from the environment to the repository variable. Pause distribution during the cutover. Once the new workflows are on `main`, disable or remove the separate App-only **Restrict creations** ruleset. Remove the old environment copy of the immutability variable, `TESTFLIGHT_TAG_CREATION_RULESET_ID`, `TESTFLIGHT_APP_CLIENT_ID`, and `TESTFLIGHT_APP_PRIVATE_KEY`. Uninstall the dedicated App from this repository once its workflows have switched. The retained ruleset continues to protect existing tags and protects new tags on creation. [GitHub ruleset layering](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/about-rulesets).
4. Verify the ruleset settings as repository owner. The [preflight](../Scripts/xcode-cloud.mjs#L125-L142) checks active tag rules and coverage. The standard token cannot reliably see bypass actors because GitHub reveals them to callers with ruleset write access. Check for other active rulesets that restrict tag creation. [GitHub repository rulesets API](https://docs.github.com/en/rest/repos/rules#get-a-repository-ruleset).

With creation unrestricted, other people and automation with repository write access can create tags under this prefix, including tags independently selectable in Xcode Cloud. Treat repository write access as permission to nominate source for the Apple manual start path. Direct Apple starts use the checks in the selected checkout, so the trust decision includes who can supply that checkout and who can start builds in Apple. The GitHub Actions path still checks CI on each request.

## Scope the App Store Connect key

1. Create or retain the `appstore-connect` environment with **Selected branches and tags** and exactly one **Branch** rule for `main`. Set the environment secret `APP_STORE_CONNECT_ENV_PRIVATE_KEY` from the original `.p8` file and set the environment variables `APP_STORE_CONNECT_ISSUER_ID` and `APP_STORE_CONNECT_KEY_ID`. If the original file is unavailable, issue a replacement and revoke the old key after confirming the replacement. [GitHub deployment environments](https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/manage-environments).
2. In GitHub Settings, confirm the environment owns the key and remove any repository-scoped `APP_STORE_CONNECT_ENV_PRIVATE_KEY` or legacy `APP_STORE_CONNECT_PRIVATE_KEY`. The workflow checks the `main` branch policy and uses the environment's key reference. The standard token cannot list repository or environment secret metadata as the dedicated App did, so verify scope and duplicates in Settings. [GitHub Actions secrets API](https://docs.github.com/en/rest/actions/secrets).

## Configure Xcode Cloud

1. After the change reaches `main`, wait for its **CI** push run to pass.
2. For the first tag-based setup, drain or cancel pending builds and deactivate the old branch distribution workflow. Create **TestFlight (verified tags)** for this repository and the `NotificationManager` scheme, with one required iOS Archive action. A fresh tag-based workflow keeps historical branch builds out of its rebuild list. Reuse the tag-based workflow from PR #13 if it already exists. Store its ID as `XCODE_CLOUD_WORKFLOW_ID` in the `appstore-connect` environment.
3. As `ttakanawa`, open **Actions → Xcode Cloud configuration → Run workflow** on `main`. Run `plan` to see missing GitHub setup and the [desired configuration](../infra/xcode-cloud/testflight.json#L9-L22). Before setting up the environment, you can get the same output by running the [script](../Scripts/xcode-cloud.mjs#L349-L354) locally with Node.js and the `plan` argument. With the Apple key and workflow ID in place, `plan` reads Apple and shows any proposed changes. After verifying the prerequisites, run `apply`. The [configuration workflow](../.github/workflows/xcode-cloud-config.yml#L18-L51) requires passing `main` CI for `apply` and reads back the configuration after a change. [Apple manual start conditions](https://developer.apple.com/documentation/xcode/configuring-start-conditions#Manually-start-a-build).
4. Before enabling TestFlight distribution, validate with a non-distributing workflow. Confirm the Actions token can create the lightweight tag at a CI-passing non-default branch tip that already exists on GitHub and changes a workflow file relative to `main`. Confirm GitHub rejects updates and deletions with the ruleset's bypass list empty. Confirm that branch, pull request, and unrelated tag starts are unavailable through Apple and that Apple discovers the deployment tag, returns its canonical ref, and supplies `CI_GIT_REF`, `CI_TAG`, and `CI_COMMIT` to the [archive hook](../ci_scripts/ci_post_clone.sh#L14-L36). Exercise both start paths and verify the hook compares those values with the actual checkout. Enable the TestFlight post-action only after those checks pass. [Apple build API](https://developer.apple.com/documentation/appstoreconnectapi/post-v1-cibuildruns).

## Deploy a branch

1. For an older branch, fetch and merge updated `main` into the branch, or rebase onto it. The branch needs the same [CI workflow](../.github/workflows/ci.yml#L1-L67), [archive hook](../ci_scripts/ci_post_clone.sh#L1-L36), and [CI gate](../ci_scripts/require-ci.sh#L1-L42) as `main`. Run the [script checks](../Makefile#L115-L118) with `make test-ci-scripts` and push the branch.
2. Open **Actions → CI → Run workflow**, select the source branch, and wait for lint and both simulator jobs. Copy the full commit SHA from the successful run. For `main`, use its successful **push** run. [GitHub Actions workflow dispatch](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#workflow_dispatch).
3. As `ttakanawa`, open **Actions → TestFlight → Run workflow** on `main`. Enter the source branch and full CI SHA. The [tag job](../.github/workflows/testflight.yml#L22-L50) verifies the branch and CI, fetches the already-published branch tip without checking it out, and creates or reuses `punctual-testflight-v1-<full SHA>`. Only this job has `contents: write`. It pushes one create-only Git ref with the job's short-lived `GITHUB_TOKEN`. The REST create-ref endpoint can additionally require `Workflows: write`, which Actions cannot grant its token. GitHub supports authenticated Git pushes with `Contents: write`; this push references a commit whose workflow files are already available at a repository branch ref. If GitHub rejects the push, the job stops. [REST create-ref permissions](https://docs.github.com/en/rest/git/refs#create-a-reference), [GitHub App Git authentication](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/authenticating-as-a-github-app-installation), and [Actions token permissions](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#permissions).
4. The [Apple start job](../.github/workflows/testflight.yml#L52-L82) reads back the exact lightweight tag and checks the selected branch head and CI again immediately before each build request, including reruns that reuse a completed tag job. If the branch moved, run CI on the new head and dispatch with its SHA. A branch update after the last check cannot change which commit the tag selects. If a tag already points elsewhere, the workflow stops and leaves it protected. If Apple has yet to discover the tag, wait and retry with the same branch and SHA while the branch still points to it. A tag can remain after a blocked Apple start.
5. For a fresh build of an existing deployment tag, open the manual start dialog in Xcode Cloud and select the tag. Use a fresh manual start in place of Apple's Rebuild command. For both start paths, the [archive hook](../ci_scripts/ci_post_clone.sh#L14-L36) verifies the checked-out commit against the tag and runs distribution configuration validation. The Archive action requires Xcode Cloud's own build to pass. The Apple path has no GitHub CI query. [Apple manual start conditions](https://developer.apple.com/documentation/xcode/configuring-start-conditions#Manually-start-a-build).
