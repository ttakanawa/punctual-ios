# Deploy a branch to TestFlight

## Start a build

1. Use a branch that contains the current [TestFlight workflow](../.github/workflows/testflight.yml#L1-L36) and [archive hook](../ci_scripts/ci_post_clone.sh#L10-L25). For an older branch, rebase onto updated `main` or merge it before deploying.
2. As `ttakanawa`, open **Actions → TestFlight → Run workflow**. Select the existing repository branch in the **Branch** menu and run the workflow. GitHub runs the workflow from the selected branch. Xcode Cloud builds the branch tip it resolves when it starts the build. Run the usual [GitHub CI](../.github/workflows/ci.yml#L1-L67) independently. [GitHub manual workflow runs](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/manually-run-a-workflow).
3. The job summary reports the queued build number or ID and the App Store Connect API resource URL when Apple returns it. Use the build number or ID in **App Store Connect → Punctual → Xcode Cloud → Builds** to follow the archive and TestFlight distribution. The same Apple workflow also supports a manual branch start in Xcode Cloud. [Apple build API](https://developer.apple.com/documentation/appstoreconnectapi/post-v1-cibuildruns).

## Check the credentials and Xcode Cloud workflow

- The manual TestFlight workflow reads the repository variables `XCODE_CLOUD_WORKFLOW_ID`, `APP_STORE_CONNECT_ISSUER_ID`, and `APP_STORE_CONNECT_KEY_ID`, and the repository secret `APP_STORE_CONNECT_PRIVATE_KEY`. Use trusted branches. The owner check applies to this workflow definition, while the repository secret can also be referenced by other eligible workflows in the repository. [GitHub Actions secrets](https://docs.github.com/en/actions/how-tos/write-workflows/choose-what-workflows-do/use-secrets).
- The separate [Xcode Cloud configuration workflow](../.github/workflows/xcode-cloud-config.yml#L18-L50) runs as the owner on `main` with the existing `appstore-connect` environment and its `APP_STORE_CONNECT_ENV_PRIVATE_KEY`. Use `plan` to preview the [manual-branch configuration](../infra/xcode-cloud/testflight.json#L1-L16). Run `apply` only when authorizing the changes. It checks `main` CI and reads the configuration back from Apple. A successful plan uses the environment key and checks access with that key. [Apple manual start conditions](https://developer.apple.com/documentation/xcode/configuring-start-conditions#Manually-start-a-build).
- In App Store Connect, confirm that the configured workflow ID belongs to Punctual, that manual starts allow branches, and that it has the required iOS Archive action for the `NotificationManager` scheme. For distribution, check the Archive action’s Deployment Preparation setting and the standard TestFlight post-action’s tester group. The TestFlight job first reads the workflow using the repository key. A successful start verifies that the repository key can also queue a build. Check the Apple key’s status and role if Apple returns an authentication or authorization error. [Apple archive settings](https://developer.apple.com/documentation/xcode/configuring-your-xcode-cloud-workflow-s-actions#Add-an-archive-action) · [Apple TestFlight post-action](https://developer.apple.com/documentation/xcode/distributing-your-xcode-cloud-builds-through-testflight).

## Verify the rollout with PR #9

1. After the common change reaches `main`, rebase the PR #9 branch `icloud-local-retention` on updated `main` and check the ordinary GitHub CI for its new commit. [PR #9](https://github.com/ttakanawa/punctual-ios/pull/9).
2. When the rollout is authorized, select `icloud-local-retention` in the TestFlight **Branch** menu. Use the queued build ID to confirm the source branch and required Archive result in App Store Connect. For an archive-only trial, use an Apple configuration with distribution disabled. When tester delivery is authorized, verify the expected TestFlight group receives the build from the standard post-action.
