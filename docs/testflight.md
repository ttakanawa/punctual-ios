# Deploy a branch to TestFlight

## Protect the deployment tags in GitHub

1. Register a dedicated GitHub App and install it on `ttakanawa/punctual-ios` only. Give it **Contents: Read and write**, **Environments: Read-only**, and **Secrets: Read-only**. The latter permissions allow the workflows to verify secret names and scope. Save the App's client ID as `TESTFLIGHT_APP_CLIENT_ID` and its private key as `TESTFLIGHT_APP_PRIVATE_KEY` in the `appstore-connect` environment. [GitHub App token action](https://github.com/actions/create-github-app-token)
2. Check that no existing tags begin with `punctual-testflight-v1-`. Create two **Active** tag rulesets. Give both the tag target patterns `punctual-testflight-v1-*` and `punctual-testflight-v1-*/**/*`, with no exclusions. The second pattern covers slash-containing tag names that also match Apple's prefix. In the Rulesets API, each include pattern starts with `refs/tags/`. [GitHub tag rulesets](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/creating-rulesets-for-a-repository#using-fnmatch-syntax)
   - Enable **Restrict creations** in the first ruleset. Set the dedicated App as the sole bypass actor. Save this ruleset ID as `TESTFLIGHT_TAG_CREATION_RULESET_ID` in the `appstore-connect` environment.
   - Enable **Restrict updates** and **Restrict deletions** in the second ruleset. Leave the bypass list empty, including for the App and repository admins. Save this ruleset ID as `TESTFLIGHT_TAG_IMMUTABILITY_RULESET_ID` in the environment.
3. As repository owner, verify both target patterns, enforcement, and bypass lists in Settings before enabling distribution. The Actions preflight checks the active rules and their target patterns. GitHub exposes bypass actors only to credentials with ruleset write access, so the owner verifies those separately. Keep the App key dedicated to the two owner-only workflows and keep both rulesets active for as long as Apple can build from these tags. [GitHub ruleset API](https://docs.github.com/en/rest/repos/rules#get-a-repository-ruleset)

## Move the App Store Connect key

1. Keep the `appstore-connect` environment restricted to the **Branch** rule `main`. In that environment, set `APP_STORE_CONNECT_ENV_PRIVATE_KEY` from the original `.p8` file and set the existing issuer and key ID variables, `APP_STORE_CONNECT_ISSUER_ID` and `APP_STORE_CONNECT_KEY_ID`. If the original file is unavailable, issue a replacement key and revoke the old key after confirming the replacement.
2. Remove the repository secret `APP_STORE_CONNECT_PRIVATE_KEY`. Keep both private keys exclusively in the environment. The workflows check secret metadata before calling Apple and stop if either private key is missing from the environment or a repository-scoped copy uses one of the deployment secret names. [GitHub Actions secrets API](https://docs.github.com/en/rest/actions/secrets)

## Configure Xcode Cloud

1. After this change reaches `main`, wait for its **CI** push run to pass.
2. In Xcode Cloud, drain or cancel pending builds and deactivate the old distribution workflow. Create a fresh workflow named **TestFlight (verified tags)** for this repository and the `NotificationManager` scheme, with one required iOS Archive action. A fresh workflow keeps historical branch builds out of its rebuild list. Store its ID as `XCODE_CLOUD_WORKFLOW_ID` in the `appstore-connect` environment.
3. As `ttakanawa`, open **Actions → Xcode Cloud configuration → Run workflow** on `main`. Run `plan`, review the output, and run `apply`. The [managed configuration](../infra/xcode-cloud/testflight.json#L9-L22) allows only manual starts for the protected tag prefix. The [configuration workflow](../.github/workflows/xcode-cloud-config.yml#L18-L61) requires passing `main` CI before applying and reads back the active configuration after the update. [Apple manual start conditions](https://developer.apple.com/documentation/xcode/configuring-start-conditions#Manually-start-a-build)
4. Validate the Apple integration in a non-distributing setup before enabling the TestFlight post-action. Confirm that branch, PR, and unrelated tag starts are unavailable in App Store Connect and Xcode and rejected through the build API. Confirm that Apple discovers an authorized tag, returns its canonical ref, and supplies `CI_GIT_REF`, `CI_TAG`, and `CI_COMMIT` to the [archive hook](../ci_scripts/ci_post_clone.sh#L14-L36). The hook must compare those values with the actual checkout before validation and archive. If Apple permits a source outside the configured tag condition, keep distribution disabled. Once these checks pass, configure the TestFlight post-action and tester group on the new workflow. [Apple build API](https://developer.apple.com/documentation/appstoreconnectapi/post-v1-cibuildruns)

## Deploy a branch

1. For an older branch, fetch and merge the full updated `main` into the branch, or rebase onto it. Keep the updated [CI workflow](../.github/workflows/ci.yml#L1-L67), [archive hook](../ci_scripts/ci_post_clone.sh#L1-L36), [CI gate](../ci_scripts/require-ci.sh#L1-L42), and [script tests](../Makefile#L115-L118) together. Run `make test-ci-scripts`, then push the branch to `ttakanawa/punctual-ios`.
2. Open **Actions → CI → Run workflow**, select the source branch, and wait for lint and both simulator jobs. Copy the full commit SHA from the successful run. For `main`, use its successful **push** run. [GitHub Actions workflow dispatch](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#workflow_dispatch)
3. As `ttakanawa`, open **Actions → TestFlight → Run workflow** on `main`. Enter the source branch and the full CI SHA. The [dispatch workflow](../.github/workflows/testflight.yml#L22-L63) checks branch identity and CI for that SHA, creates the protected tag, then starts Apple by tag ID. If the branch head changed while GitHub was waiting, run CI on the new head and dispatch with its SHA. Once the verification succeeds, further branch updates cannot change the tagged commit.
4. If Xcode Cloud has yet to discover the new tag, wait and retry with the same branch and SHA while the branch still points to it. A retry can reuse the exact protected tag. A previously authorized tag remains eligible for a fresh manual tag start in Apple and always identifies the original CI-verified commit. The archive hook rejects Apple rebuilds, ordinary branch checkouts, and checkouts that differ from the SHA in the tag.
